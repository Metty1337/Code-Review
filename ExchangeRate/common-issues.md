## Архитектура и слои

### Отсутствует сервисный слой
Вся бизнес-логика не должна находиться в сервлетах/контроллерах. Стоит ввести сервисный слой, который будет содержать бизнес-логику, а контроллер оставить тонким - буквально вызов сервиса и возврат результата.

### Сервис должен возвращать DTO, а не модель
Хорошей практикой является возвращать из сервиса DTO, тем самым скрывая внутреннее устройство модели от контроллера и сохраняя границы слоев.

### Модель и DTO не разделены (смешение ответственности)
Сейчас модель используется одновременно как Entity и как DTO - нарушение SRP. Рекомендую разделить: модель предметной области для DAO слоя, а DTO - для передачи данных между сервисом и контроллером.

### Сервис не должен использовать DAO другого сервиса напрямую
Сервис не должен напрямую использовать DAO другого сервиса, если уже есть существующий сервис, который инкапсулирует работу с этим DAO. Вместо `CurrencyDao` в `ExchangeRateService` стоит использовать `CurrencyService`.

### Обработку исключений вынести в фильтр
Можно вынести "ловлю" исключений в отдельный `ExceptionHandlingFilter implements Filter`, тогда сервлеты станут тоньше и ближе к соблюдению SRP.

### Composition Root / DI через ServletContextListener
Зависимости не стоит создавать через `new` прямо в сервлетах. Рекомендую реализовать паттерн Composition Root, например через `AppInitializer implements ServletContextListener`, который создаст все зависимости и положит их в `ServletContext`.

### Синглтон - анти-паттерн в данном контексте
Синглтон нарушает SRP, создает скрытые зависимости, усложняет тестирование. Стоит явно выражать зависимости через конструктор и давать возможность их подменять.

### Fat Controller (раздутые сервлеты)
Сервлеты получились слишком объемными - антипаттерн "Fat Controller". Стоит стремиться к тонкому контроллеру: вызов сервиса и возврат результата. Валидация, обработка ошибок и бизнес-логика должны быть в других слоях.

## DAO / Работа с БД

### Не пробрасывать SQLException в верхние слои
Не стоит пробрасывать `SQLException` в верхние слои, они не должны знать про JDBC. Лучше ловить исключение в DAO и выбрасывать понятное для бизнес-логики исключение, например `DatabaseException`.

### Не использовать RuntimeException, а кастомные исключения
В случае исключения в базе данных выбрасывается обычный `RuntimeException` - стоит создать кастомное исключение, например `DatabaseException`.

```java
// вместо
catch (SQLException e) {
    throw new RuntimeException(e);
}

// лучше
catch (SQLException e) {
    throw new DatabaseException("Failed to ...", e);
}
```

### SELECT * заменить на конкретные столбцы
Вместо `SELECT *` лучше конкретно прописать запрашиваемые столбцы. Таким образом при изменении schema приложение будет работать корректно.

```java
// вместо
"SELECT * FROM currencies"

// лучше
"SELECT id, code, full_name, sign FROM currencies"
```

### Использовать Optional вместо null
Никогда не возвращай `null` - это повышает шанс NPE. Для случаев, когда объект может быть не найден, идеально подходит `Optional`.

```java
// вместо
public Currency findByCode(String code) {
    ...
    return null;
}

// лучше
public Optional<Currency> findByCode(String code) {
    ...
    return Optional.empty();
}
```

### Бизнес-исключения не должны выбрасываться в DAO
Выбрасывание `NotFoundException` или других бизнес-исключений в DAO - нарушение SRP. DAO не должен знать о бизнес-логике. Лучше возвращать `Optional` или количество обновленных строк и обрабатывать в сервисе.

### N+1 проблема
Метод имеет проблемы с производительностью из-за N+1 проблемы. Решение - использовать `JOIN` в SQL запросах, чтобы сразу вытягивать связанные данные.

### SQL запросы в текстовые блоки
Текст SQL запроса удобнее читать, когда он логично разбит на строки. Для этого можно использовать текстовые блоки.

```java
// вместо
String sql = "SELECT id, code, full_name, sign FROM currencies WHERE code = ?";

// лучше
String sql = """
    SELECT id, code, full_name, sign
    FROM currencies
    WHERE code = ?
    """;
```

### ResultSet через try-with-resources
`ResultSet` реализует интерфейс `AutoCloseable`, поэтому лучше его использовать через try-with-resources для предотвращения утечки ресурсов.

### Дублирующийся маппинг ResultSet в объект - вынести во вспомогательный метод
Повторяющийся код маппинга ResultSet в объект стоит вынести во вспомогательный метод, например `mapRow(ResultSet rs)`.

### Пробрасывать cause в исключение
Обязательно при возможности пробрасывать cause в исключение, а не "съедать" его.

```java
// вместо
catch (SQLException e) {
    throw new DatabaseException("Error message");
}

// лучше
catch (SQLException e) {
    throw new DatabaseException("Error message", e);
}
```

### Интерфейсы для DAO
Отсутствуют интерфейсы для DAO, из-за чего не представляется возможной замена реализации и использование полиморфизма. Было бы большим плюсом добавить интерфейсы.

## Исключения

### Exceptions as control flow - анти-паттерн
Использование исключений как механизма ветвления логики (try-catch вместо if-else) - анти-паттерн. Исключения дороги по производительности и предназначены для ошибок, а не для управления потоком. Лучше использовать `Optional` и вспомогательные методы.

```java
// вместо (анти-паттерн)
try {
    return findDirect(base, target);
} catch (NotFoundException ignored) {}
try {
    return findReverse(base, target);
} catch (NotFoundException ignored) {}

// лучше
return findDirect(base, target)
        .or(() -> findReverse(base, target))
        .or(() -> findCross(base, target))
        .orElseThrow(() -> new ExchangeRateNotFoundException(base, target));
```

### Сообщения об исключениях на английском
Все сообщения об исключениях должны быть написаны на английском языке.

```java
// вместо
throw new NotFoundException("Валюта с кодом %s не найдена".formatted(code));

// лучше
throw new NotFoundException("Currency with code %s not found".formatted(code));
```

### Не пробрасывать пустое исключение
Не стоит выбрасывать исключение без сообщения, нужно добавлять контекст.

```java
// вместо
throw new SQLException();

// лучше
throw new SQLException("Insert failed: no rows affected");
```

## Именование и конвенции

### Пакеты в единственном числе
В Java пакеты обычно называются в единственном числе: `servlet` вместо `servlets`, `model` вместо `models`, `exception` вместо `exceptions`.

### DAO в CamelCase
Классы в Java называют в стиле UpperCamelCase, включая аббревиатуры. Правильно: `CurrencyDao`, `ExchangeRateDao`. Неправильно: `CurrencyDAO`, `ExchangeRateDAOImpl`.

### DTO в CamelCase
Обычно аббревиатуру DTO не пишут заглавными буквами и придерживаются PascalCase: `CurrencyDto` вместо `CurrencyDTO`.

### Именование DAO реализаций
Названия `CurrencyDAOImpl` недостаточно информативны. Более хорошим вариантом было бы `JdbcCurrencyDao` - из названия сразу понятна технология.

### static final, а не final static
В Java принято писать модификаторы в порядке: `private static final`, а не `private final static`.

### Публичные методы сверху, приватные снизу
Стандартный стиль большинства Java-проектов - публичные методы стоят сверху, приватные снизу. Таким образом, когда кто-то открывает класс, он сразу видит публичный API, а детали реализации скрыты ниже.

### Именование методов сервиса
Для сервиса название `create` подходит больше, чем `save`. `save` больше подходит для DAO слоя.

## Утилитарные классы

### final модификатор и приватный конструктор
Все утилитарные классы должны иметь модификатор `final` и приватный конструктор.

```java
// вместо
public class ErrorHandler {}

// правильно
public final class ErrorHandler {
    private ErrorHandler() {}
}
```

## Модели / DTO

### Long вместо int для id
Концептуально для `id` лучше подходит `Long` вместо `int` или `Integer`.

### BigDecimal для rate
Для работы с денежными значениями и курсами валют стоит использовать `BigDecimal` вместо `double`.

### DTO должны быть иммутабельными
DTO должен быть неизменяемым объектом: приватные поля, конструктор, геттеры, без сеттеров. Идеально подходит `record`.

### record для DTO
`record` идеально подходит для DTO - он иммутабелен и автоматически генерирует конструктор, геттеры, equals, hashCode, toString.

### Не передавать null как id при создании
Вместо передачи `null` в качестве id при создании объекта лучше создать отдельный конструктор без id.

## Код / Качество

### Магические числа/строки заменять константами
В проекте встречаются магические числа/строки, которые имеют бизнес-значение - их стоит выносить в константы.

### Комментарии - признак сложного кода
В большинстве случаев комментарии - признак трудно читаемого кода, который необходимо переписать. Стоит сделать код самодокументируемым за счет декомпозиции и хороших имен методов. Подробнее: Мартин, "Чистый Код", гл.4, Комментарии.

### Убирать закомментированный код
Закомментированный код стоит убирать перед коммитом. Он засоряет кодовую базу и всегда доступен через историю git.

### Неиспользуемый код удалять
Неиспользуемые методы, классы и импорты стоит удалять. Они засоряют кодовую базу.

### Использовать логгер вместо System.out/err и e.printStackTrace()
Вместо `System.out.println`, `System.err.println` и `e.printStackTrace()` стоит использовать логгер (SLF4J / java.util.logging).

```java
// вместо
e.printStackTrace();
System.out.println(e.getMessage());

// лучше
log.error("Error message", e);
```

### Не игнорировать замечания IDEA
Не стоит игнорировать замечания от IntelliJ IDEA - почти всегда они по делу. Также рекомендую использовать Reformat Code (Ctrl+Alt+L).

### Декомпозиция больших методов
Методы получились довольно объемными и плохо читаемыми. Стоит воспользоваться вспомогательными методами для улучшения читабельности. Идеальный метод расчета курса:

```java
public ExchangeDto getExchange(String base, String target, BigDecimal amount) {
    return findDirect(base, target)
            .or(() -> findReverse(base, target))
            .or(() -> findCross(base, target))
            .orElseThrow(() -> new ExchangeRateNotFoundException(base, target));
}
```

### Stream API - разбивать на строки по операциям
При использовании Stream API стоит разбивать цепочку на несколько строк по операциям для читабельности.

```java
// вместо
return dao.findAll().stream().map(Mapper::toResponse).collect(Collectors.toList());

// лучше
return dao.findAll()
          .stream()
          .map(Mapper::toResponse)
          .collect(Collectors.toList());
```

### Constructor Injection вместо инициализации в полях
Для зависимостей класса стоит использовать Constructor Injection, а не инициализировать их прямо в полях. Это делает зависимости явными и упрощает тестирование.

```java
// вместо
public class CurrencyService {
    private final CurrencyDao currencyDao = new CurrencyDao();

// лучше
public class CurrencyService {
    private final CurrencyDao currencyDao;

    public CurrencyService(CurrencyDao currencyDao) {
        this.currencyDao = currencyDao;
    }
```

## REST API / Валидация

### Недостаточная валидация входных данных
Хотелось бы видеть валидацию для всех полей: код валюты (длина и формат), имя валюты (длина), символ валюты (длина). При отсутствии нужного поля - показывать пользователю конкретное сообщение с кодом 400.

### POST должен возвращать 201, а не 200
POST эндпоинты в случае успешного создания ресурса должны возвращать HTTP 201 (Created), а не 200 (OK).
